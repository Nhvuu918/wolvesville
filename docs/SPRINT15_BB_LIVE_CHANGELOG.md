# v1.7.19 — live B/B QA integration (WIP)

The published rules remain wolvesville-official-v1.3.3. Each new QA match has an immutable initial `qaProfile` in its existing SQLite kernel archive; the profile is separate from the published version. Existing official matches without this profile retain their prior rules. No separate candidate journal is copied into the match archive. The coordinator uses the existing `withGameMutation` and the kernel's transaction/event ledger/replay. `qaPack` is stored in the state snapshot, not a parallel store. Live endpoints are disabled without explicit local QA opt-in. SQLite only is supported for the QA launch script. No database schema changes.

- Pack QA [9,25,48,74,76]: pack ballot and Snow Angel protection only. Leader gets two bites only when the last living wolf, so the two-wolf scenario admits ONE target. Initial representative order is a deterministic QA fixture, not the outstanding gameplay policy BB-PENDING-02. All other individual abilities and official voting are intentionally unavailable in this QA scenario. Day advance is an explicit QA stage, not a new official rule. Consensus commits death and protection to the actual archive, and winner check uses existing stable parity/death ledger. No AFK fallback; missing response waits. Candidate multi-target and retaliation tests remain separate.
- Trap QA [5,10,25,74]: persistent mark lives in participant effects. Two placements across distinct nights, private observation results; actual accepted action resolves, then mark consumed. Existing RNG and resource accounting. No new pack bite/voting or victory admitted for this scenario.
- Trap Guard QA [5,10,25,31,74]: staged setup, placement on night 1, guard from night 2, regardless of chosen target. Prior mark + valid guard charges ordinary history/cooldown, removes only newly created protection and applies direct elimination through the bounded runtime/death ledger. This avoids imposing same-night ordering. Poison, rescue, cross-window and revival interaction are NOT live-supported. A simultaneous unsupported interaction must fail closed. These are QA constraints, not official gameplay changes.
- Authentication uses the existing room membership checks. Pack endpoint stores individual last valid choices with revision/idempotency; empty retains previous. Only eligible wolves receive their own choices and shared waiting status, not others' individual votes. Existing WS projections refresh after commits. Trap state is visible to the engineer only. `STATE_COMMITTED` is internal. Replay verifies profile and fixture representative order unchanged.
- Earlier diagnostic pack tests accidentally allowed two targets with multiple wolves; source audit of Character #48 exposed this violation. These logs are retained and NOT acceptance evidence. Corrected max target policy and retested.

Unresolved policies: BB-PENDING-01 waiting timeout/fallback, BB-PENDING-02 representative order for real matches, BB-PENDING-03 cross-window group. No new official R/F/A/B/C/atomic or normal-deck certificate is claimed from QA profiles.
